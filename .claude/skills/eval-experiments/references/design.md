# Design the evaluation, one decision at a time

Ask with **AskUserQuestion**: one question, two to four options, the recommended one first with "(Recommended)". Before each question write one or two lines on why it matters; after each answer confirm in one line what was settled. Skip what the request already answers. With "you decide", take the recommended options.

| Step | Question | Typical options |
|---|---|---|
| 1 · Decision | Which decision must this evaluation support? | Choose between two configurations (Recommended) · Check one version before shipping · Find where the app fails |
| 2 · Configurations | What changes between the experiments? | One component at a time: retriever, `k`, prompt, model, chunk size. Name both values. Two configurations is enough for a first evaluation |
| 3 · Questions | Where do the questions come from? | Real questions of the process, anonymized (Recommended) · Written by a person who knows it · Never generated by the app under test. Include colloquial ones, codes or figures, and at least one the documents cannot answer |
| 4 · References | Who writes the expected answer of each question? | A person of the process, from the documents (Recommended) · Expected file and page only (retrieval evaluation, no judge) |
| 5 · Evaluators | How is each answer scored? (multiSelect; then build each one with `references/evaluators.md`) | Code: expected page retrieved (Recommended) · Code: every citation was retrieved (Recommended) · Code: the reference's figures are in the answer · Judge: correct against the reference · Judge: grounded in the fragments |
| 6 · Calibration | Only with a judge. Which answers labeled by a person? | 8 or more fixed answers, half correct and half with typical errors (wrong figure, incomplete, invented data, another product's rule) (Recommended) · Reuse labels the team already has |
| 7 · Size | How many questions per run? | A small subset first (5, one per question type) and the full set once the first run is read (Recommended) · The full set directly |

## Which evaluator for which need

| Need | Evaluator | Why |
|---|---|---|
| Did the right fragment arrive? | Code: expected file and page in the retrieved ones | Free, deterministic; separates retrieval failures from generation failures |
| Does every citation point to something retrieved? | Code: parse `[file, p. N]` and compare | A citation can be invented; a regex finds it |
| Is the answer correct? | Judge with the reference | Paraphrases and partial answers need reading, not string matching |
| Is every claim in the fragments? | Judge with the context, no reference needed | Catches made-up figures even when the reference is missing |
| Is the judge trustworthy? | Agreement with answers labeled by a person | The judge is another AI app: it can prefer long answers or answers like its own |
| Is it fast and cheap enough? | Latency and tokens of each answer | A small quality gain can cost more than it is worth |
| Did the agent use the right tools, route or plan? | Code over the trajectory (`references/agents.md`) | An answer can be right by luck; the trajectory explains why it is wrong |

## Close the design with a plan

Before writing code, show: the decision, the two configurations, the dataset (name, number of questions, who wrote the references), the evaluators and what each one measures, the calibration set, and the cost of one run: calibration calls (one per labeled answer), experiment calls (examples × (1 answer + judgements per answer)) per configuration, traces (one for the calibration grouped in `trace(...)` + one per example per experiment with `disable_evaluator_tracing=True`) and the experiments it leaves. Ask for confirmation: "Run it like this (Recommended)" · "Change something".
